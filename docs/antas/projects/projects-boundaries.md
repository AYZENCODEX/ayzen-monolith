# Projects module boundaries (PRJ-01)

## Scope and compatibility

Projects stays inside the existing API server. `routes/projects.ts`,
`routes/project-dates.ts` and `routes/project-templates.ts` remain the only
HTTP surface and keep every path, method, middleware chain, registration order,
response shape, authorization decision and PEP wiring. PRJ-01 moves no code and
changes no behavior. It fixes the owner of every route and symbol, records the
cross-module contract, and adds a blocking validator
(`pnpm validate:projects-boundaries`) so later phases cannot drift.

The machine-readable source of truth is
`scripts/antas/projects/boundaries.manifest.json`. This document explains it.
The cross-module decisions (Vault, Finance) are in
`projects-cross-module-contract.md`.

## Import rules

- Projects sources may import from Vault or Finance only through the allowlist in
  the manifest (`allowedCrossModuleImports`): exact specifier and exact symbol
  set. Today that is two Vault imports. Anything else fails.
- Vault and Finance must not import Projects code. Verified: zero reverse edges.
- `projects/domain` stays pure: it may import only sibling domain files.
- `projects/` must not import `routes/*`. Routes become adapters over `projects/`.
- No import cycle may include a Projects source. Verified: none today.
- A direct read of a table owned by another module is allowed only if listed in
  `knownForeignTableEdges` with a resolving phase. Five exist today (below).

## Known edges, recorded and not endorsed

Projects route sources reading tables owned elsewhere (`knownForeignTableEdges`):
`vault_entries` (PRJ-05), `finance_ledger_entries` (PRJ-04), `tasks`,

## PRJ-03 status: ratings and templates extracted

Ratings (5 routes in `routes/projects.ts`) and templates (8 routes in
`routes/project-templates.ts`) now run through `application/ratings.ts` and
`application/templates.ts`. The route handlers keep their paths, middleware,

`routes/project-templates.ts` is a pure adapter. The ratings handlers stay in
`routes/projects.ts` as thin calls, because that file also holds routes owned by

Decisions made while extracting:

- The `projects_updated` realtime broadcast for a rating is emitted from the use
  case, after the write and before the response, as the route did. It comes from
  `lib/event-hub`, so `projects/` still imports nothing from `routes/`.
- `projects-repo.ts` now exists with two read queries: a typed lookup (rating
  existence check) and the raw `SELECT *` that `from-project` needs, because
  `category`, `duration_type`, `difficulty` and `cost_type` are not in the Drizzle
  definition. Templates therefore read projects only through the projects
  repository and never create or update a project, which replaces the roadmap's
  original "no forked project creation" gate.
- `PROJECT_TEMPLATE_DATA_KEYS` lives in the DB schema package, so the pure template
  rules take the allow-list as a parameter and the use case supplies it.
- `ratings-repo.ts` left-joins `users` for the author name. That moved edge is
  recorded, and the foreign-table scan now covers module files, not only route files.
- `project_ratings` and `ayzen_project_templates` may be touched only by their own
  repository, with one read-only exception: Vault's snapshot repository. Vault's
  restore code refers to these tables by registry name and restores rows generically;
  the validator cannot see that, so it is recorded as an unscanned dynamic consumer.

Core project CRUD (`GET/POST/PATCH/DELETE /projects`, `GET /projects/:id`) is also extracted into
`application/projects.ts`; the handlers in `routes/projects.ts` are thin calls. `formatProject` moved
to `domain/project.ts` (it was used only by these handlers). Side effects keep their order: write, realtime
broadcast, best-effort Telegram alert (create only), response. `getOptionalUserId` stays in the adapter because
it reads the Authorization header. `routes/ai-actions.ts` is left untouched: its project insert stays a
recorded parallel writer whose resolution is undecided (see below).

### Findings preserved, not fixed

1. **Unescaped SQL (`PRJ-ISSUE-1`).** `deadline` (POST and PATCH) and `startedAt` (PATCH) are put into raw SQL
   without escaping. Every other raw field escapes single quotes. Only admin/moderator (POST) or admin (PATCH)
   can reach it. A characterization test pins the current behavior and says so. It needs its own approved
   change because a fix rejects or alters values that work today.
2. **FIXED after PRJ-07: `POST /projects` may return 500 after creating the project (`PRJ-ISSUE-2`).** The response is now built by `formatCreatedProject` from the typed insert row, with raw columns added from the `RETURNING *` row. Original description: When the body carries any
   raw-SQL-only field, the handler runs `UPDATE ... RETURNING *` and passes the raw row to `formatProject`.
   `lib/db` has no snake-to-camel mapping, so if the driver returns `created_at`, `createdAt.toISOString()`
   throws after the insert and broadcast. Reproduced against the original handler with a snake_case fake;
   **not confirmed on a real database**, so confirm before calling it a bug. `PATCH` handles raw rows
   explicitly; `POST` does not.

`routes/ai-actions.ts` still inserts into `projects` directly and runs a raw `UPDATE` of
`total_roi_distributed`. It keeps its current behavior (no broadcast, no Telegram alert); unifying it with
`POST /projects` is a separate decision.

## PRJ-04 status: ROI / P&L extracted

`GET /projects/:id/roi-summary` and the four receipt routes (mint, revoke, public card, public PDF) now run
through `application/roi-receipts.ts`. The handlers in `routes/projects.ts` keep their paths, middleware, PEP
audit actions (`project_pnl_receipt.view`, `project_pnl_receipt.pdf`), status codes, error bodies and try/catch
layout. PDF streaming stays in the adapter: the use case returns a layout spec and the route hands it to
`lib/receipt-theme`.

**Decision D2' (supersedes D2).** Projects owns project-level ROI and P&L and the public receipts end to end.
The roadmap's plan was to call Finance's existing P&L use case; PRJ-01 found it was not equivalent, and the
original D2 proposed a new Finance per-project use case. D2' keeps the arithmetic in Projects instead,
because the two calculations already differ (raw sums plus `roiPct` here; base-currency conversion plus
`interestOwed` in Finance) and moving the receipt math into Finance would change which module owns it for no
numeric gain. The one ledger read is isolated in `project-ledger-reader.ts` (raw `SUM` per kind) and recorded as
an accepted foreign-table edge. No Finance file changed, Projects imports nothing from Finance, and PRJ-04 does
not depend on Finance's WP-8/WP-9 pack. See `projects-cross-module-contract.md`.

What is pinned: no rounding and no currency conversion; receipts print amounts with a `$` prefix whatever
currency the rows were recorded in; `roiPct` is `null` only with no spend and no earnings; a stored entity ROI
of `0` is kept (`??`, not `||`). The validator fails if `routes/projects.ts` reads the ledger, the ROI table or
the receipts table again, or if `computeProjectPnlSummary` is redeclared there.

Not decided: whether receipts should convert to base currency like `/finance/investments`. That would be a
visible numeric change and needs its own approval.

## PRJ-07: enrollment billing (team and bulk enroll now charge credits)

**The gap.** Single enroll (`POST /projects/:id/enroll`) charges the metered action `workspace.project_use`
(2 credits at the current price). Team enroll (`POST /teams/:id/enroll-project`) and bulk enroll
(`POST /projects/bulk-enroll`) created the same enrollment rows and charged nothing. The project owner confirmed this is a
billing gap.

**The fix.** Both now use the shared `application/enrollment-billing.ts`:

- **What is charged:** `workspace.project_use`, once per enrollment row actually created, to the user performing the
  action (the leader, for team enroll).
- **When:** the balance for the whole quantity is checked before any write, and the charge happens after the writes,
  as in single enroll. The check is quantity-aware because `chargeCredits` charges nothing when the balance is too low,
  so a one-unit check would let a large request through for free. `hasCreditBalance` gained an optional `quantity`
  argument that defaults to 1, so every existing caller is unchanged.
- **Insufficient balance:** `402` with the same `OUT_OF_CREDITS` body shape as single enroll, plus `quantity` and
  `required`, and nothing is written.
- **Nothing created, nothing charged:** a team whose members are all already enrolled, a bulk request where every row
  conflicts, and a join-only team enroll (no `vaultEntryId`) charge nothing.
- **Response:** both gain an additive `_credits` field (the charge, or `null`), like single enroll.
- **If the post-write charge fails** (a concurrent spend), the enrollments stay and `_credits` is `null`, exactly as
  single enroll behaves; nothing is rolled back.

**Guard.** The validator fails if `teams.ts` or `bulk.ts` stops checking and charging through the shared helper, or if
a new file writes `project_enrollments` without being billed or explicitly exempt (`services/sync.ts` is exempt: it only
deletes).

**Assumptions to confirm.** Team enroll is charged to the leader, not the members. The price equals single enroll with no
bulk discount. The bulk pre-check uses the requested count as an upper bound, so a request that would partly conflict can
be refused when the balance covers only the new rows.

**New finding (PRJ-ISSUE-4, probable, not confirmed on the live database).** No unique constraint on
`project_enrollments (project, user, entity)` exists in the Drizzle schema or any `.sql` file in the repo, so bulk
enroll's `ON CONFLICT DO NOTHING` probably never conflicts and repeating a bulk enroll likely inserts duplicate rows.
Because each inserted row is now charged, repeating a bulk enroll charges again. Recommended follow-up: skip entities that
