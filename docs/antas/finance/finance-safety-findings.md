## Fixes applied (F1, F2)

- **F1:** `runFinanceRecurringSweep(options?: { userId?: number })`; the due-rule query moved unchanged into `finance/jobs/due-rules.ts` (`selectDueRecurringRules`) with an optional user filter. `run-now` now reads the caller (401 if absent) and passes `authUser.userId`, so a user only runs and sees counts for their own rules. The scheduled cron still calls the sweep with no options and processes everyone. Response shape is unchanged.
- **F2:** `postJournal` now returns `null` before opening the transaction when any line names an account code missing from the book, instead of dropping the line and storing an unbalanced journal. It uses the same null contract as the existing unbalanced and too-few-lines rejections, which the manual journal route already maps to HTTP 400. All hard-coded posting codes in the codebase are system accounts, and user-defined accounts in the book still work (tested).
- Behavior changes to review: `run-now` result counts shrink from global to per-user; a manual journal naming a missing account now fails instead of being stored short.

- **F3:** Chart-of-accounts codes are now unique per `(user_id, book_id, code)`. `POST /finance/books` already documents that every book gets its own seeded chart, but the old `UNIQUE(user_id, code)` index made that seeding fail for any second book. The in-code migration list creates `finance_accounts_user_book_code_idx` (after `book_id` exists and is backfilled) and then drops the old index; `migrations/122_finance_multi_book_accounts_and_repayment_idempotency.sql` does the same for hand-applied SQL. Duplicate codes within one book are still rejected.
- **F4:** `applyPrincipalRepayment` is one statement computing amount and status together (no stale `partial` with amount 0) and returns `null` for a missing entry. New `recordRepayment` writes the repayment row and the balance/interest change in one transaction (a failed decrement now rolls the row back) and supports an optional idempotency key: header `Idempotency-Key` or body `idempotencyKey`, stored in a new nullable `finance_repayments.idempotency_key` column with a partial unique index on `(entry_id, idempotency_key)`. Same key and same repayment replays the original (HTTP 200, `Idempotent-Replayed: true`, nothing re-applied); same key with a different amount/type returns 409. Without a key behavior is as before, so existing clients are unchanged; protection is opt-in. The key is not exposed in responses.
- Additional behavior changes to review: a repayment against a deleted entry now returns 404 instead of 201; `finance_repayments` gains a nullable column and unique index (additive); the old accounts unique index is dropped.
- **Deployment order matters:** the repayments table is now read and inserted with the new column, so migration 122 (or the boot-time migration list) must be applied before this code serves traffic, or every repayment read/write fails.

- **F5:** `deleteJournalForEntry` now runs in one transaction and deletes lines and headers by the same id set (the old header delete matched by `source_ledger_entry_id`, so a journal inserted between the lookup and the delete lost its header but kept orphan lines). The real exposure was wider: `DELETE /finance/entries/:id` ran four separate deletes (repayments, amortization, journals, entry), so a mid-way failure could strip an entry of its history while the entry survived. It now calls the new `deleteLedgerEntryCascade(entryId, userId)`, one transaction that also re-checks ownership itself (the earlier deletes used to be keyed on entry id alone, protected only by the route's pre-check). Returns false and deletes nothing for another user's or a missing entry (HTTP 404, unchanged). What it still does not do: lock against a journal posted concurrently for the same entry, or delete invoice lines/attachments (unchanged behavior).

- **F6:** `payAmortizationInstallment` (installment payment) and the payment-agreement verify route are now each one transaction. Both claim their row first with a conditional update (installment `status <> 'paid'`; agreement `status = 'passkey_confirmed'`), so two concurrent requests can no longer both record a payment: the loser gets `already_paid` (installment, same response as before) or HTTP 409 (agreement). The repayment row, the entry balance and status (one SQL statement), interest paid, and for agreements the invoice `paidAmount` and status (one SQL statement) commit or roll back together; journal postings and the invoice event stay best-effort after commit. Behavior changes to review: a concurrent or repeated agreement verification now returns 409 instead of double-posting; the invoice status is derived from the database's current amount rather than the amount read at the start of the request. The agreement-verify path has static gates only: `finance_invoices` and `finance_payment_agreements` are not in the isolated test schema yet.

- **F7:** `contributeToGoal` is one `UPDATE` that increments `current_amount`, flips `active` to `achieved` at the target, and requires `linked_asset_id IS NULL` and the caller's `user_id` in the same `WHERE`; only when nothing updates does it look up the goal to answer `not_found` or `linked_asset`. Concurrent contributions serialize on the row lock, so none is lost. Arithmetic is double precision, as the JS it replaces, so results match. The old update also ignored `user_id`; the new one does not. Behavior unchanged otherwise: non-active goals keep their status, responses are the same.
