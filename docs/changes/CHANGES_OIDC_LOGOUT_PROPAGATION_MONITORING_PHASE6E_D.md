# OIDC Roadmap — Season 3, Phase 6e-d: Monitoring

Phase 6e-c-এর নিজের কথায়, "যা ইচ্ছাকৃতভাবে এখানে নেই" সেকশনে: *"`oidc.backchannel_logout.*`-এর জন্য structured metrics/dashboards/alerting (এই পাসে শুধু `logger`/`logBus` call যোগ হয়েছে, কোনো নতুন observability infrastructure না) — **6e-d (Monitoring)**।"* এই পাস ঠিক সেই reserved scope — migration 087-এর `ayzen_oidc_backchannel_logout_queue` টেবিলটা (6e-c) এখন যা ইতিমধ্যে durably রেকর্ড করছে, সেটার উপর একটা read-only stats/health/alert লেয়ার।

## যা যোগ/পরিবর্তন করা হলো

| ফাইল | পরিবর্তন |
|---|---|
| `artifacts/api-server/src/lib/oidc-logout-propagation.ts` | **আপডেট** — 6e-c-এর উপর appended: `getBackchannelLogoutQueueStats()` (windowed + all-time status counts, oldest-pending-age, recent dead-letter samples), `computeBackchannelLogoutQueueHealth()` (pure threshold check) + `evaluateBackchannelLogoutQueueHealth()` (effectful wrapper), `alertAdminsOfDeadLetteredBackchannelLogout()` (নতুন — admin email alert); `processBackchannelLogoutQueueRow()`-এর `dead_letter` branch এখন এই alert ফাংশন কল করে |
| `artifacts/api-server/src/routes/admin-oidc-backchannel-logout.ts` | **নতুন** — `GET /admin/oidc-backchannel-logout/status`: stats + health একসাথে রিটার্ন করে, `requireDev`-গেটেড |
| `artifacts/api-server/src/routes/index.ts` | নতুন router import + `adminOidcRolloutRouter`-এর ঠিক পাশে mount |

## ডিজাইন — কেন এই শেপ

- **নতুন in-memory tally না — টেবিলটাই already সোর্স অফ ট্রুথ।** `lib/oidc-login-attempts.ts` (Phase 5c-d/5e) একটা in-memory ring buffer ব্যবহার করে কারণ login attempts-এর কোনো durable টেবিল নেই — সেই ফাইলের নিজের "WHY IN-MEMORY, NOT A TABLE" নোট অনুযায়ী। Back-Channel Logout queue-র ক্ষেত্রে উল্টো: migration 087 (6e-c) থেকেই এটা একটা durable Postgres টেবিল। তাই "metrics" মানে এখানে শুধু সেই টেবিলটা query করা — একটা সমান্তরাল কাউন্টার রাখার কোনো কারণ নেই।
- **stats/health split ঠিক `oidc-login-attempts.ts`-এর precedent অনুসরণ করে।** `getBackchannelLogoutQueueStats()` (effectful, DB পড়ে) আর `computeBackchannelLogoutQueueHealth()` (pure, শুধু ইনপুট স্ট্যাটস-এর উপর থ্রেশহোল্ড চেক) আলাদা — ঠিক `getOidcLoginAttemptStats()` বনাম `evaluateOidcRolloutHealth()`-এর মতোই, যাতে টেস্ট স্ক্রিপ্ট থ্রেশহোল্ড লজিক লাইভ DB ছাড়াই যাচাই করতে পারে। `evaluateBackchannelLogoutQueueHealth()` একটা পাতলা wrapper যেটা দুটো জোড়া লাগায় — কিন্তু admin route নিজেই এটা কল করে না (নিচে দেখুন) ডাবল-fetch এড়াতে।
- **Route নিজে `computeBackchannelLogoutQueueHealth()` কল করে, `evaluateBackchannelLogoutQueueHealth()` না।** `evaluateBackchannelLogoutQueueHealth()` নিজের ভেতরে stats fetch করে — route যদি সেটা কল করত, stats আলাদাভাবে আবার fetch করতে হতো response-এ ফেরত দেওয়ার জন্য, মানে একই ডেটার জন্য দুটো DB round trip। Route একবার `getBackchannelLogoutQueueStats()` কল করে, তারপর সেই একই object pure ফাংশনে পাস করে — `routes/admin-oidc-rollout.ts`-এর নিজের `Promise.all([...])` batching যে discipline মেনে চলে, এটা সেই একই discipline।
- **Health check শুধু dead_letter count না, pending backlog age-ও দেখে।** একটা dead_letter row মানে "চেষ্টা করে হাল ছেড়ে দিয়েছি" — একটা real per-target failure। কিন্তু worker যদি silently বন্ধ হয়ে যায় (`startBackchannelLogoutQueueWorker()` কখনো কল না হওয়া, বা deploy-এ cron miss হওয়া), তাহলে **কোনো** dead_letter row-ই তৈরি হবে না — সব row `'pending'`-এই আটকে থাকবে চিরকাল, যেটা দেখতে "queue খালি এবং সুস্থ" থেকে আলাদা করা যাবে না যতক্ষণ না কেউ oldest pending row কতক্ষণ ধরে অপেক্ষা করছে সেটা চেক করে। এটা ঠিক `lib/vault-backup-alerts.ts`-এর `alertUserOfMissedBackup()`-এর নিজস্ব "silence looks like nothing to report" গ্যাপের সমতুল্য, এই queue-তে প্রয়োগ করা।
- **`maxPendingBacklogAgeMs` default 10 মিনিট — backoff ceiling (30 মিনিট) থেকে ছোট, ইচ্ছাকৃতভাবে।** একটা single row legitimately backoff করে 30 মিনিট পর্যন্ত pending থাকতে পারে নিজের থেকেই — সেটা normal, alarm না। এই থ্রেশহোল্ড instead worker-এর নিজের poll interval (15s)-এর উপর ভিত্তি করে সেট করা: একটা সুস্থ worker একটা due `'pending'` row এক poll tick-এর মধ্যেই claim করে, পুরো একটা backoff cycle অপেক্ষা করে না। 10 মিনিট সেই tick interval-এর তুলনায় যথেষ্ট generous slack, কিন্তু একটা genuinely-stalled worker ধরার জন্য যথেষ্ট টাইট।
- **Alert ঠিক একবার fire হয়, transition-এর মুহূর্তে — repeat না।** `alertAdminsOfDeadLetteredBackchannelLogout()` কল হয় `processBackchannelLogoutQueueRow()`-এর dead_letter branch থেকে, ঠিক row-টা dead_letter-এ move হওয়ার সময়। যেহেতু `'dead_letter'` টার্মিনাল status (আর কখনো re-claim হয় না), এই branch শুধু একবারই রান হয় প্রতিটা row-এর জন্য — তাই duplicate alert email-এর কোনো ঝুঁকি নেই, আলাদা কোনো "already alerted" ফ্ল্যাগ ছাড়াই।
- **Alert email `db`/`usersTable`/`eq` (drizzle) দিয়ে, queue-এর নিজের raw `pool` দিয়ে না।** এই ফাইলের বাকি queue কোড raw `pool` ব্যবহার করে কারণ সেটা queue টেবিলের নিজস্ব established convention (6e-c-এর নিজের ডিজাইন নোট দেখুন)। কিন্তু admin lookup (`role = 'admin'` সব ইউজার) `usersTable`-এর বিপরীতে, queue টেবিলের বিপরীতে না — তাই সেটা সেই টেবিলের নিজস্ব established access pattern অনুসরণ করে (`lib/dr-test-cron.ts`-এর `alertAdminsOfFailure()`, `lib/vault-backup-alerts.ts`-এর `alertAdminsOfStaleKeyRotation()`)। একই যুক্তিতে `sendEmail` ইম্পোর্ট করা হয়েছে, নতুন কোনো email-sending কোড লেখা হয়নি।
- **একটা admin-এর bounced email অন্যদের ব্লক করে না, আর dead_letter transition-কেও ব্লক করে না।** `alertAdminsOfFailure()`/`alertAdminsOfStaleKeyRotation()`-এর ঠিক একই discipline: প্রতিটা admin-এর email আলাদা try/catch-এ, একজনের ব্যর্থতা বাকিদের email পাঠানো থামায় না। আর পুরো alert ফাংশনটাই `processBackchannelLogoutQueueRow()`-এ `.catch()`-সহ কল হয় — row-এর `status = 'dead_letter'` update ততক্ষণে already commit হয়ে গেছে, তাই alert email ব্যর্থ হলেও সেই DB write প্রভাবিত হয় না।
- **Route GET-only, কোনো admin action নেই।** `routes/admin-oidc-rollout.ts`-এর মতো PATCH নেই এখানে — 6e-c-এর নিজের "যা ইচ্ছাকৃতভাবে এখানে নেই" নোট অনুযায়ী কোনো dead-letter replay/requeue endpoint এখনো এই roadmap-এর স্কোপে নেই। 6e-d-এর নিজের কাজ ছিল "metrics/dashboards/alerting define করা", নতুন admin action যোগ করা না।

## যা ইচ্ছাকৃতভাবে এখানে নেই

- Dead-lettered row replay/requeue করার কোনো admin endpoint — উপরে বলা হয়েছে, এটা 6e-d-এর স্কোপে ছিল না।
- কোনো external metrics/dashboarding সিস্টেম (Datadog, Grafana ইত্যাদি) ইন্টিগ্রেশন — `GET /admin/oidc-backchannel-logout/status` নিজেই "dashboard"-টা, `oidc-login-attempts.ts`-এর নিজের precedent-এর মতোই একটা in-app JSON read, বাইরের কোনো observability infrastructure না।
- **Full end-to-end verification** (real login → real revoke → real ব্যর্থ delivery → real retry → real dead-letter → real alert email, লাইভ DB-সহ) — **6e-e (E2E Logout Verification)**, roadmap-এর নিজের পরের ও শেষ sub-phase।

## টেস্ট

`scripts/src/test-oidc-backchannel-logout-monitoring.ts` কাভার করে (pure function, কোনো live DB ছাড়াই): quiet/healthy বেসলাইন, dead-letter count থ্রেশহোল্ডের ঠিক নিচে/উপরে দুই দিকেই আচরণ (`>`, `>=` না — থ্রেশহোল্ডের সমান কাউন্ট নিজে থেকে ট্রিপ করে না), pending backlog age থ্রেশহোল্ডের নিচে/উপরে, দুটো থ্রেশহোল্ডই একসাথে ক্রস হলে দুটো reason-ই রিপোর্ট হওয়া (শুধু প্রথমটা না), `oldestPendingAgeMs: null` কখনো backlog চেক ট্রিপ না করা, আর result-এ stats/thresholds অবিকৃতভাবে echo হওয়া।

**DB-নির্ভর অংশ এই পাসে exercise করা হয়নি** — `getBackchannelLogoutQueueStats()` (চারটা real query), `evaluateBackchannelLogoutQueueHealth()` (উপরেরটার wrapper মাত্র), আর `alertAdminsOfDeadLetteredBackchannelLogout()` (real `usersTable` query + real `sendEmail()` কল)। এগুলো 6e-b/6e-c-এর নিজস্ব একই precedent অনুযায়ী লাইভ dev DB/email config-এর বিপরীতে হাতে-verify করা দরকার — migration 087-এর একটা row-কে dead-letter পর্যন্ত নিয়ে গিয়ে (6e-c-এর টেস্ট ফাইলের নিজের বর্ণিত ম্যানুয়াল ফ্লো ব্যবহার করে), তারপর `GET /api/admin/oidc-backchannel-logout/status` কল করে `countsInWindow.deadLetter`/`recentDeadLetters`-এ সেটা প্রতিফলিত হচ্ছে কিনা, আর admin alert email সত্যিই পৌঁছাচ্ছে কিনা — দুটোই চেক করা উচিত।

**পরিবেশগত সীমাবদ্ধতা (এই পাসে):** এই sandbox-এ network/`pnpm install` অ্যাক্সেস নেই, তাই কোনো টেস্ট স্ক্রিপ্ট (নতুন বা বিদ্যমান) বাস্তবে চালিয়ে দেখা যায়নি এখানে — 6e-a/6e-b/6e-c-এর নিজস্ব একই সীমাবদ্ধতা। বাস্তব dev পরিবেশে `pnpm install`-এর পর `npx tsx scripts/src/test-oidc-backchannel-logout-monitoring.ts` চালিয়ে নিশ্চিত করা দরকার।

## পরবর্তী সাব-ফেজ

**6e-e — E2E Logout Verification**: real login → real revoke → real ব্যর্থ delivery → real retry → real dead-letter (আর এখন, real alert email) — সম্পূর্ণ ফ্লো একটা লাইভ dev DB-সহ end-to-end যাচাই করা। এটাই Phase 6e-এর, এবং পুরো Season 3-এর, শেষ sub-phase।
